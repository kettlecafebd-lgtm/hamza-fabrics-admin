# Supabase Egress Audit — `hamza-fabrics-admin`

**Date:** 2026-11-12
**Scope:** entire `src/` tree (~19,000 LOC / 75 JSX components & pages), build config, nginx, deployment config
**Symptom under investigation:** Supabase Egress **36.5 GB** (730 % of plan), Cached Egress **0.33 GB** → **~99.1 % of bytes leave the origin uncached**

---

## 0. Read this first — where the Supabase calls actually are

**This repository contains no Supabase client, no Supabase SDK and no `.select()` calls.** It is a Vite + React 19 SPA that talks to a Node/Express backend over `VITE_API_URL` (default `http://localhost:5000`). Every byte of Supabase egress is generated by that backend, triggered by the 147 `fetch()` call sites catalogued below.

Verification (run from the repo root):

```bash
$ grep -rn "\.select(" src/                     # 1 hit — inputRef.current.select()
$ grep -rn "from(['\"]" src/                    # 0 hits
$ grep -rni "supabase" src/ package.json        # 0 hits
$ grep -n "supabase" .env .env.example          # 0 hits
```

So the audit is split into two halves, and **both are required** to fix the bill:

| Layer | Owned by | What it does wrong | Share of the 36.5 GB |
|---|---|---|---|
| **A. This repo (frontend)** | you | Requests *entire tables* with no `limit`, re-requests them after every mutation/keystroke, and renders full-resolution images into 40 px boxes | ~90 % of the *request volume* |
| **B. Backend (`hamza-fabrics-api`, not in this checkout)** | you | Executes those requests as `select('*')` with no projection and no server-side paging | 100 % of the *bytes* (it is the only thing holding a DB connection) |

Everything in **Part A** is a literal file:line fix. Everything in **Part B** is a one-line change per route, given in §1 and §5. If you only fix one side, the bill will not move.

> **Blast-radius math.** `/api/orders` returns every order ever created, and each row carries a denormalised `products` JSON blob (line items, *including a full-size image URL per item*). At 8,000 orders × ~1.8 KB of JSON + joined customer, one page load of the Orders screen pulls **~15 MB**. An operator who opens Orders, changes 6 statuses, and assigns 4 couriers does that **11 times** (`fetchData()` after every mutation — `Orders.jsx:236, 246, 285, 407`) = **~165 MB for ten minutes of work, for one admin.** Ten staff × 20 sessions/month ≈ **33 GB**. That is the whole bill, in one screen.

## 1. `.select('*')` queries — exact locations and columns the UI actually needs

### 1.1 Result of the search

There are **zero** literal `.select('*')` or `.select()` calls in this repository — it has no database access at all. The equivalent problem lives in the backend, and it can be found in one command there:

```bash
# in the backend repo
rg -n --type js "\.select\(\s*(\*|)\)" .          # explicit select('*') / select()
rg -n --type js "\.select\(\)" .                  # PostgREST defaults to all columns
rg -n --type js "\.select\(['\"][^'\"]*['\"]\s*\)" | grep -v ":"   # sanity: no projections
```

**Expected effect:** the `orders` payload shrinks by the `products` JSON blob, which is the dominant term. On a typical fabric order (2–4 line items, each with name + sku + price + qty + image URL) that is **55–75 % of the row**. > ⚠️ `order.products` **must not be dropped blindly** — `OrderTable.jsx:124, 212`, `Orders.jsx:157–166, 372, 482` and `ThermalSticker.jsx:35` all read it. The safe cutover is server-side aggregation (below) plus the lazy-detail patch in §5.4.

### 1.4 Stop storing line items as a JSON blob on the order

`order.products` is a **JSON string** (`ThermalSticker.jsx:35` and `CustomerAIProfile.jsx:64` both do `typeof order.products === 'string' ? JSON.parse(...)`). It is denormalised, unqueryable, and it duplicates a full image URL per line item.

Recommended normalisation (one migration, enables everything else):

```sql
create table if not exists public.order_items (
  id          bigint generated always as identity primary key,
  order_id    bigint not null references public.orders(id) on delete cascade,
  product_id  bigint references public.products(id),
  variant_id  bigint references public.variants(id),
  name        text    not null,
  sku         text,
  qty         int     not null default 1,
  unit_price  numeric(12,2) not null default 0,
  selected_size text,
  image_url   text          -- keep the URL, never the bytes
);
create index on public.order_items (order_id);

-- one-time backfill from the existing blob
insert into public.order_items (order_id, product_id, name, sku, qty, unit_price, selected_size, image_url)
select o.id,
       nullif((i->>'productId'), '')::bigint,
       coalesce(i->>'productName', i->>'name', 'Unknown'),
       coalesce(i->>'sku', i->>'sku_code'),
       coalesce(nullif(i->>'qty','')::int, nullif(i->>'quantity','')::int, 1),
       coalesce(nullif(i->>'price','')::numeric, 0),
       i->>'selected_size',
       i->>'image'
from public.orders o
cross join lateral jsonb_array_elements(
  case when jsonb_typeof(o.products::jsonb) = 'array' then o.products::jsonb else '[]'::jsonb end
) as i;
```

Then serve list rows with a cheap aggregate instead of the blob:

```sql
create or replace view public.order_list_view as
select o.*,
       coalesce(i.items_count, 0) as items_count,
       coalesce(i.items_total_qty, 0) as items_total_qty
from public.orders o
left join (
  select order_id, count(*) items_count, sum(qty) items_total_qty
  from public.order_items group by order_id
) i on i.order_id = o.id;
```

`OrderTable.jsx` only needs `items_count` in the collapsed row; the expandable panel fetches `/api/orders/:id/items` on click.

Good news first: **there is no React Query, no SWR, no `refetchInterval`, and no infinite render loop in this codebase.** All 72 `useEffect` call sites terminate. The problem is not loops — it is *fan-out*: one user action fans out into many full-table requests.

There is no shared cache anywhere. Even the paged screens refetch from zero on every mount. Minimum viable fix, no new dependency:

```js
// src/lib/queryCache.js — 30 lines, replaces the need for SWR on read paths
const store = new Map();               // key -> { data, at }
const TTL = 30_000;

export async function cachedJson(key, fetcher, ttl = TTL) {
  const hit = store.get(key);
  if (hit && Date.now() - hit.at < ttl) return hit.data;
  const data = await fetcher();
  store.set(key, { data, at: Date.now() });
  return data;
}
export const invalidate = (prefix) => {
  for (const k of store.keys()) if (k.startsWith(prefix)) store.delete(k);
};
```

`/api/taxonomy`, `/api/courier/active`, `/api/settings/system` and `/api/marketing/settings` are the obvious candidates — all are small but fetched on nearly every navigation.

## 4. Base64 images and large JSON blobs inside database tables

### 4.1 Confirmed in this repo

| Finding | Location | Detail |
|---|---|---|

| **`orders.attachments` is a JSON array** | `OrderTable.jsx:324` (`order.attachments?.length`), `Orders.jsx:46` | Fetched for every row but only `.length` is ever rendered. If the backend ever stores uploaded files inline here, this one column explains the bill on its own. |
| **Base64 data URIs do exist in memory** | `ResolutionCenter.jsx:37–41` | `FileReader.readAsDataURL` — used **for previews only**; the actual upload is `multipart/form-data` (`:64–70`). | **Settings snapshot cached in `localStorage`** | `Settings.jsx:245` | `JSON.stringify(settings)` including `heroImages[]`, `heroMobileImages[]`, `footerImages[]`. ### 4.2 Not verifiable from this repo — check it yourself

The frontend accepts `image_url` as either absolute or relative (`CommandMenu.jsx:180`, `VariantMatrix.jsx:123`) and never inspects the scheme, so **a `data:image/...;base64` value would render silently**. That is exactly how a base64 column hides for months. Run these against the database:

```sql
-- 1. Any column that looks like it stores image bytes
select table_schema, table_name, column_name, data_type
from information_schema.columns
where table_schema not in ('pg_catalog','information_schema')
  and (column_name ~* '(image|photo|avatar|attachment|file|blob|base64|data_url)'
       or data_type in ('bytea'));

-- 2. Any row actually holding a data URI (the smoking gun)
select 'orders.products' as where_, count(*) as bad_rows
from public.orders
where products::text like 'data:image%' or products::text like '%base64,%'
union all
select 'orders.attachments', count(*)
from public.orders
where attachments::text like '%base64,%'
union all
select 'products.image_url', count(*)
from public.products
where image_url like 'data:%';

-- 3. How many megabytes those blobs cost, per table
select 'orders' as t,
       pg_size_pretty(sum(octet_length(coalesce(products::text,'')))) as products_json,
       pg_size_pretty(sum(octet_length(coalesce(attachments::text,'')))) as attachments_json,
       pg_size_pretty(avg(octet_length(coalesce(products::text,'')))) as avg_row_products
from public.orders;

-- 4. Storage buckets: are the originals enormous?
select bucket_id,
       count(*) as objects,
       pg_size_pretty(sum((metadata->>'size')::bigint)) as total,
```

### 4.3 Full-size images in 40 px slots (confirmed, high impact)

21 `<img>` tags; exactly **one** had `loading=`. The order table renders a 40×40 thumbnail from `prod.image` — **the original upload** — for every line item of every row (`OrderTable.jsx:222`). With 50 rows × 3 items that is 150 full-resolution requests per page, all uncached on first paint, all re-validated on every navigation.

Three-part fix:

1. **Serve a derivative, not the original.** Supabase Storage Image Transformations, gated behind an env flag so it is a no-op until you enable transforms in the dashboard:

```js
// src/utils/imageUrl.js  (added in this branch)
const PUBLIC_OBJECT_SEGMENT = '/storage/v1/object/public/';
const RENDER_SEGMENT = '/storage/v1/render/image/public/';
const transformsEnabled = import.meta.env.VITE_SUPABASE_IMAGE_TRANSFORMS === 'true';

export function thumbUrl(url, width = 96, quality = 70) {
  if (!url || typeof url !== 'string' || !transformsEnabled) return url;
  if (!url.includes(PUBLIC_OBJECT_SEGMENT)) return url;   // external/relative untouched
  const rendered = url.replace(PUBLIC_OBJECT_SEGMENT, RENDER_SEGMENT);
  const sep = rendered.includes('?') ? '&' : '?';
  return `${rendered}${sep}width=${width}&quality=${quality}&resize=cover`;
}
```

2. **Never lazy-load the lightbox.** `Orders.jsx:510` (enlarged image) must keep the original URL — clicking a thumbnail should request the full image once.

3. **Persist the derivatives.** Upload a `thumb_` variant to Storage at upload time so even non-Supabase hosts serve small files, and keep `image_url` for the lightbox.

### 5.10 Make the CDN carry the read traffic (the 0.33 GB → multi-GB fix)

Cached egress is 0.33 GB against 36.5 GB uncached. Nothing in the stack is telling the browser or CDN that responses are reusable. Two levels:

**Static assets — already added in this branch** (`nginx.conf`, `vercel.json`): immutable `max-age=31536000` for `/assets/*` and `/fonts/*`, `max-age=2592000` for `/bangladesh.geojson`, and a 7-day `Cache-Control` on `/uploads/*` (previously served with **no** cache header at all).

**Live API — pick one:**

- *Safest:* add `ETag` + honour `If-None-Match` in the backend so a repeat poll returns `304` with no body. This alone removes most of the `AdminHeader`/settings traffic.
- *Best:* put a 30–60 s `s-maxage` in front of genuinely shared, non-personalised reads:

```nginx
location ~ ^/api/(taxonomy|courier/active|settings/system|marketing/settings)$ {
    proxy_pass http://backend:5000;
    proxy_cache api_cache;
    proxy_cache_valid 200 60s;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
    proxy_cache_lock on;
    add_header X-Cache-Status $upstream_cache_status always;
}
proxy_cache_path /var/cache/nginx/api levels=1:2 keys_zone=api_cache:10m max_size=512m inactive=10m use_temp_path=off;
```

Do **not** cache `/api/orders`, `/api/customers`, `/api/rma/*` or anything under `/api/brain/*` — they carry authenticated, per-user data.
